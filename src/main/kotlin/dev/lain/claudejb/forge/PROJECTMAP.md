## What lives here

**Two read-only questions about the branch that is checked out**, asked of GitHub or GitLab over HTTP: the
pull/merge requests open from it, and its last CI run. There is no write path — nothing here opens, closes,
merges or comments on anything — and there is no background poll: the questions are asked when the Git view
is drawn and at no other time.

**Being opt-in is a network decision, not a feature flag.** Every call reaches a server named by the
repository the user happens to have open, so storing an access token for that host **is** the consent.
Without one, `ForgeService` stops at the token lookup, `ForgeProbe` is never asked, and the package opens no
socket at all.

**The shape is build → fetch → parse, and that is what makes it testable.** Naming and signing a request, and
decoding a reply, are pure functions of their inputs — unit-tested over recorded JSON with no network
anywhere near the suite. `ForgeHttp.fetch` is the single impure step between them, and it knows nothing about
either provider.

## Conventions here

- **One token per HOST, never per provider.** A GitHub Enterprise Server and github.com both say "GitHub", and
  so do a self-managed GitLab and gitlab.com. Keying on the provider would send a company server's credential
  to a public API the moment somebody cloned a public repository — the credential-scope mistake
  `SecretStore.envOverlay` already exists to prevent one layer down. The host is the only key under which that
  cannot happen, and `ForgeTokens.normalizeHost` is what makes two spellings of one host one key.
- **The safe is reached through `SecretStore`'s read/write pair, never `PasswordSafe` directly.** That pair is
  the test seam: it is inert in a test JVM that has not installed a store of its own, so a suite can never
  read or write the developer's real keychain. A door onto the safe that skips it is a door a test leaks
  through.
- **Nothing here throws.** DNS, TLS, a timeout, a redirect we refuse, a 5xx and a malformed body are the same
  event to a card that should simply not draw, so each becomes a `Silent` carrying an enum and **no message,
  no URL and no header**. That shape is also what keeps the token out of an exception message, which is the
  classic way a credential reaches a log nobody meant to write.
- **Off the EDT, always.** Every entry point blocks. `ForgeService` refuses on the EDT and says so in the log
  rather than hopping threads — an answer delivered after the caller returned is worse than none — exactly as
  `git/GitHistoryService` refuses to run `git log` there.
- **Nothing here logs a token, a signed URL or a header**, and `ForgeTokens` logs nothing at all: a failed
  read and "no token" are deliberately indistinguishable.
- **A third provider is three edits in three places** — a `ForgeProvider` value, a `ForgeApi` implementation
  and a row in `apiFor` — deliberately not a flag. Each provider brings its own endpoints, its own auth header
  and its own status vocabulary, and pretending otherwise is how a "generic" client ends up with a `when` in
  every method.

## Minefields here

- **`ForgeRequest` is deliberately NOT a `data class`, and that is its entire reason for being a class at
  all.** Its `headers` carry the access token — `Authorization: Bearer …` on GitHub, `PRIVATE-TOKEN: …` on
  GitLab — and a generated `toString()` prints every property, so the credential rides into the first log
  line, exception message or debugger label that ever interpolates one of these. That is how a token escapes
  without anybody writing a line that logs it. `toString` names the URI and nothing else, and
  `ForgeSecrecyTest` fails the build if that stops being true. Converting it to a `data class` for `equals`
  is the change to refuse.
- **`Silent` is for the log and never for the user.** The card is omitted **entirely** — no placeholder, no
  greyed panel, no "configure me" prompt. The user did not ask for a forge integration, and an IDE that nags
  about a feature nobody enabled is worse than one that stays quiet. The reason exists so a support question
  can be answered from `idea.log`; the UI's only correct reaction is to draw nothing.
- **`NOT_VISIBLE` folds 403 and 404 on purpose.** Both providers make "does not exist" and "your token cannot
  see it" indistinguishable, which is what stops a token being used to enumerate private repositories.
  Splitting them here would undo that from the client side.
- **A GitLab 401 on the version endpoint is a POSITIVE identification, not a failure.** That route requires a
  token, so only a host that *has* it can answer 401 at all; GitHub answers 404. Reading the 401 as an error
  is how `ForgeProbe` silently stops recognising every self-managed GitLab.
- **No second remote-URL parser, ever.** `ForgeRepo` is an input built in `ui/GitIntegration` from what
  `git/GitRemoteInfo` parsed. Two parsers for one format is the defect this repository has already paid for
  once, and there must be no `fun parse(remoteUrl: String)` in this package.
- **`ForgeHttp.USER_AGENT` is a browser string and the trade is recorded at the declaration.** Sending one is
  not optional — GHES rejects a request without it, while api.github.com accepts the JDK default, so omitting
  it works for everyone on the public service and fails only for self-hosted users. What it costs is that an
  administrator cannot tell from their own log which client is calling, and the literal ages. Read that KDoc
  before touching it.
- **`MAX_RESPONSE_BYTES` is not a tidiness bound.** Without it a host that streams forever — a captive portal,
  a misconfigured proxy, a compromised endpoint — turns a card into unbounded heap on a background thread.
- **The probe's verdict is cached for the IDE's lifetime, the negative included.** That is deliberate: a host
  does not change which forge it runs, and without caching the miss an unrecognised server would be probed on
  every dashboard push. It also means a host that was briefly unreachable stays "unknown" until the IDE
  restarts.
