## What lives here

What the user hands the agent from the IDE: the open file, the selection, the diagnostics, a picked file, a
pasted image. This is the IDE-intelligence side of the composer's `@`-mentions and Attach menu.

The package is split so that **the parts that can be tested are pure and the impure part is only the process
spawn**: `ImageAttachments` decides bytes → data URL and the size and type rules, `ClipboardCli` decides the
argv and the preferred clipboard type, and neither of them runs anything.

## Conventions here

- **Keep the decision pure and the effect thin.** A rule that lives inside a function that also spawns a
  process cannot be tested, and this package's rules are exactly the kind that get an edge case wrong.
- Clipboard work happens **off the EDT, with a deadline**. A hung Wayland clipboard must not freeze the IDE.
- Bounds are checked at the edge: an oversized or unsupported attachment is refused here, not deeper in.

## Minefields here

- **AWT clipboard *reads* are broken under the native Wayland toolkit**, while writes work. That asymmetry is
  the whole reason `ClipboardCli` exists.
- The Wayland clipboard bug was fixed twice before it was fixed correctly: **the fault was the trigger, not
  the read.** The embedded browser's web clipboard is isolated from the system clipboard, so the paste event
  never reached the host at all — the host-side read was unreachable code until the composer was told to
  route the keystroke straight to the host.
- Copied image *files* arrive as `text/uri-list`, not as image bytes. Handling only the image type silently
  drops the most common way a user pastes a screenshot from a file manager.
- The helper binaries are not on a fixed path; they are resolved across the common bin directories.
