## What lives here

The end-to-end suite: a **real IDE**, driven through RemoteRobot, against the sandbox project in
`resources/sandbox-project/`. It is the only layer that exercises the plugin the way a user does — tool
window, tabs, composer, dashboard, Settings page — and therefore the only one that can catch a feature that
is implemented, tested and unreachable from the UI.

It is **gated off by default** (`-PuiTest.enabled=true`) and runs nightly, because it needs a display and
takes minutes rather than seconds.

## Conventions here

- **`UiTestBase` owns the setup**, and a test that reimplements it will diverge from it.
- **Point at the UI that exists.** A locator written against a surface that has since been replaced still
  compiles and still runs; it just stops proving anything.
- One user-visible journey per test. This layer is slow, so breadth of coverage is bought elsewhere.
- The sandbox project stays minimal: it is a fixture, not a demonstration.

## Minefields here

- **The fixture in `resources/sandbox-project/` must be a git repository of its own.** Git resolves a
  working tree by walking **upwards**, so with no `.git` of its own the fixture resolves to *this*
  repository — and any Git action a test exercises there lands on the plugin's own working tree rather than
  on a fixture. `UiTestBase.requireSandboxIsItsOwnGitRepo` demands it and **deliberately does not repair
  it**: a harness that writes to the tree in order to run is the same defect wearing another face.
- **A locator that no longer matches usually fails as a timeout**, which reads like an environment problem
  and gets retried rather than fixed.
- This suite is **not in the default `test` task**. Nothing here runs on an ordinary local gate pass, so it
  goes stale silently between nightly runs.
- It needs a display. On a headless runner that means Xvfb, and without it every test fails for the same
  uninformative reason.
