# Claude Code for JetBrains — native plugin

IntelliJ Platform plugin (Kotlin/JVM; everything visible is JCEF, Swing only where the platform demands it — tool window, menus, dialogs) that integrates Claude Code into JetBrains IDEs, with a rich native GUI (streaming chat, permission-gated diff review, plan-mode, sessions, IDE intelligence fed to the agent). Goal: surpass AI Assistant and the official plugin (currently just a terminal launcher). Built to present to Anthropic.

## Core decision
**No Node or TS SDK at runtime.** Speaks Kotlin/JVM **directly with the `claude` binary** via `stream-json` + control over stdio. The TS SDK is just a wrapper that spawns the same binary; we replicate it in Kotlin. `node_modules/@anthropic-ai/claude-agent-sdk/` (`sdk.d.ts`, `sdk-tools.d.ts`, `sdk.mjs`) is kept **as protocol reference only**, not distributed.

Decisions: (1) **JCEF** (embedded Chromium web view) for the chat UI — the transcript, composer, and permission/dashboard cards are now an inlined web app (see "## JCEF UI (4.0.0)" below; the original Swing chat UI was deleted in 4.0.0). **Diffs remain native** via the IDE's `DiffManager` — that part of the original decision still holds. (2) **Preinstalled `claude` binary required** (PATH + `~/.local/bin` detection; if missing → actionable notification and abort). (3) **Auth reused** from the binary (subscription/OAuth or `ANTHROPIC_API_KEY`).

**Behavioral principle:** UX parity with the original Claude Code, consuming the SDK's **structured protocol** (`stream-json`/control) — "using the SDK" means its contract, not the npm package. **Never mirror raw CLI output**: do not dump terminal-formatted text; reconstruct every state/command **natively** from the event's structured fields (e.g. compaction from `status`/`compact_metadata`, cost from `get_session_cost`). `system/local_command_output` is the antipattern to avoid.

## Protocol (stream-json + control)
One process per session, kept alive in streaming-input mode. Key flags (`--print` is **mandatory**):
```
claude --print --output-format stream-json --input-format stream-json --verbose \
       --permission-prompt-tool stdio [--include-partial-messages] [--permission-mode <m>] \
       [--model <m>] [--resume <id>] [--allowedTools …] [--setting-sources user,project,local]
```
- stdin: `{"type":"user","message":{"role":"user","content":"…"},"parent_tool_use_id":null}` (one line = one JSON). `cwd`=project root, `env` inherited.
- stdout: `system/init` (carries `session_id`, `slash_commands`), `assistant` (content blocks), `stream_event` (deltas), `result` (end of turn), `keep_alive` (ignore), control frames.
- **Control** (correlated by `request_id`): the binary emits `control_request{subtype:"can_use_tool",tool_name,input,title}` → host responds `control_response{subtype:"success",response:{behavior:"allow",updatedInput}}` or `{behavior:"deny",message}`. Host→binary: `initialize`, `interrupt`, `set_model`, `set_permission_mode`, `get_context_usage`, `get_session_cost`, `mcp_status`.

**Who writes the file:** on `allow`, **the binary writes** (not the IDE). Therefore, before approving Edit/Write we reconstruct the proposed content and open a **diff in an editor tab** (`SimpleDiffRequest`→`ChainDiffVirtualFile`→`FileEditorManager.openFile`; NOT `DiffEditorTabFilesManager.showDiffFile`, which opens a window). Approval = **inline non-modal card** (Accept/Reject/View diff), never dialogs. After writing, refresh VFS (`VfsUtil.markDirtyAndRefresh`).

Since the onboarding rework the PRIMARY path is **card-driven and fully native**: `ClaudeLoginFlow` runs `claude auth login` under a PTY (NOT `setup-token` — its reduced grant drops scopes Claude Code exercises, file upload among them), driven by the JCEF sign-in card through the `LoginUi` seam (`attachUi`/`detachUi`, implemented by `OnboardingController`). The card is ONE browser step: the binary opens the browser itself (the host must NOT also call `BrowserUtil.browse` — that opened a second tab) and captures the callback, so the code field is an optional fallback on the same screen; `submitCode` writes `\r`, not `\n`, because the Ink TUI is in raw mode and only `\r` submits (an `\n` hung the card on "Verifying"), with a 45s watchdog behind it. **`CredentialsVault` is what keeps the credential off the disk**: `auth login` writes `~/.claude/.credentials.json` (plaintext on Linux, shared with the terminal CLI), so the vault harvests it into `SecretStore.CREDENTIALS_JSON` (the IDE **PasswordSafe**) and DELETES it — including a login made in the user's own terminal, deliberately. **Nothing ever writes that file back** (`materialize` was removed): the credential reaches the binary as `CLAUDE_CODE_OAUTH_TOKEN` via `CredentialsVault.envOverlay`, which takes precedence over the binary's own store (verified on 2.1.223 — `auth status` flips `authMethod` from `claude.ai` to `oauth_token`). Two consequences, both real and both accepted: (1) only the binary can spend the refresh token, and it does so by rewriting that file, so an expired token is simply **not an identity** (`hasUsableToken()` false → sign-in card) rather than a session that fails its first turn; (2) the `oauth_token` identity is REDUCED — `auth status` then returns `authMethod`/`apiProvider` and no email or plan — so the dashboard's plan falls back to `CredentialsVault.subscriptionType()` off the vaulted blob, and the email is genuinely unavailable by this route. `harvest()` runs at `launch()`, at `stop()`, and in the boot watcher, but NEVER while `LoginCoordinator.inProgress` — `auth login` finishes by writing that very file, and harvesting mid-flow deleted it under the binary and broke the browser leg, leaving code-paste as the only route that worked. `CredentialsVault.homeOverride`/`inertHere()` make the vault refuse to touch a real home from a test JVM: the integration tests start a real session, whose `launch()` harvested the developer's own credentials into a throwaway test safe and deleted them — invisible while the file was still written back, destructive the moment it wasn't. `CREDENTIALS_JSON` is file-shaped and deliberately NOT in `SecretStore.envOverlay`. The **API key is not in `SecretStore` at all**: it lives in its own provider slot (`ClaudeSettings.setProviderApiKey(Provider.ANTHROPIC, …)` → `providerApiKey:anthropic`), the same mechanism DeepSeek uses, so the card and Settings ▸ Provider are two doors onto one credential and no provider's key can overwrite another's; `effectiveLaunchEnv()` applies it only when the selected provider IS Anthropic. Credentials are env only, NEVER argv, never logs/transcript/XML. **`ApiKeyApproval`** closes the bug that made a valid key look invalid: the binary demands each `ANTHROPIC_API_KEY` be approved once and records the last 20 chars in `~/.claude.json` → `customApiKeyResponses.approved`; under `--print` there is nobody to ask, so an unapproved key is refused. Typing it into the card IS that answer, so the approval is written (amending the file, never replacing it) and the key is then validated with `AuthCli.status` before being stored at all. Fallbacks in order: IDE terminal (`auth login`) → dialog-driven PTY → manual notice. `ClaudeSession.needsLogin` raises the card proactively and reactively (`LoginDetection` on failed turns / auth errors) — and the plugin's auth identity is **exclusively** what it holds securely (`SecretStore` or an explicit Settings env var): with nothing held, the state is logged-out BY DEFINITION, no probe run, because the binary would answer from the terminal CLI's own store, a separate identity the plugin never reads. **Sign-in precedes the boot screen**: `start()` refuses to launch without a credential (`hasCredential`) — verifying auth needs no session, and launching one we know is unauthenticated buys a spawned process and a turn that fails for a reason already known at click time. And the three boot states are RE-DERIVED, not remembered: `refreshBootState()` runs every 3s off-EDT while no session is up, so installing the binary or signing in outside the card takes effect without closing the tab (detection used to happen once, inside `start()`, which is why a tab opened before the install kept its stale answer forever). A held credential is validated via `AuthCli.status` (run with `effectiveLaunchEnv()`, or a safe-held token reads as logged-out). `/login` is no longer advertised in the palette (sign-in is a BUTTON on the card and the dashboard account row, which also offers Log out = **the safe cleared, nothing else** — `auth logout` from an IDE button would kill the user's terminal login), but a typed `/login` still works as a silent alias; the card's skip button is labelled as consent to ride the terminal's login for the session.

- `permission/PermissionBroker` — receives `can_use_tool`, **does not block**; auto-approves (bypass/acceptEdits) or hands off a `PendingPermission` to the UI. **`forceAsk` (5.5.0)** is checked BEFORE the mode *and* before `isRemembered`, and that order is the whole point: forcing `permissionMode` to `default` would NOT have worked, because `PermissionBroker` reads `if (!allowedByMode && !isRemembered(...))` — a tool with "Always allow" recorded would still auto-approve. It only ever downgrades an approval to a card; a guard `DENY` stays a `DENY` and nothing here can allow what would otherwise have been asked. Wired from `ClaudeSession.gitIntegration`, i.e. per SESSION rather than per turn — the Git chat is its own tab, so there is no window in which the forcing lapses. The failure mode is silent (a prompted action would just run), so `PermissionBrokerMatrixTest` pins all four cases, "beats Always allow" included. Actual resolution in `ClaudeSession.resolvePermission`/`resolveQuestion`. **"Always allow" is a PRE-authorisation now, and that is a change of its nature rather than a new door onto it**: the set (`ClaudeSettings.alwaysAllowTools`, read by `isRemembered`) used to be granted only by answering a real permission card for that tool, and Settings offered nothing but revocation — a tool could not be auto-approved before it had asked at least once. The composer's ⚙ menu (`JcefSettingsMenu`, group *Always allowed tools*) grants it to any built-in having asked for nothing. What makes that a trade and not a hole is what still runs in front of it: `SensitiveGuard` executes BEFORE any auto-approval and has no opt-out, so a credential path, a dangerous command, the system temp directory and foreign territory still raise a card for a tool that is always allowed, and the broker still refuses to auto-approve a reviewable write outside the project root. The set widens what may run unasked INSIDE the project, never what the guard lets past. The key arrives from a browser, so it is VERIFIED and not trusted: `always:<Tool>` is accepted only when the suffix is in `ToolNaming.BUILTIN_TOOLS`, and the same rule covers every composite key the menu emits (`model:`, `effort:`, `mode:`, `source:`, `allow:`, `deny:`) — each re-checked against the catalogue its row was built from, which is why "closed set" stays true. `SensitiveGuard` (the deterministic lock that runs BEFORE any auto-approval) was split in 5.5.0 into `CredentialPaths`, `CommandRules`, `ForeignTerritory`, `GuardPaths` (canonicalisation, the `pathCandidates` walk) and `ToolInputScanner`, with `SensitiveGuard` itself left as the verdict. **`ToolInputScanner` owns PROVENANCE, and that is a security decision, not a parsing detail**: an input's keys are not interchangeable — a *location* key (`file_path`, `path`, …) names where the call will act, a *command* key names a shell line whose tokens must each be judged, and a *content* key (`old_string`, `new_string`, `content`, …) is payload the call is CARRYING, not a place it is going. Offering content keys as locations is how editing a line that merely quotes `/home/bob/.cache/app` became a hard FOREIGN `DENY` with no override — a rule cannot tell a quotation from a destination, so the distinction has to be made before the rule runs. The asymmetry is the whole point and must survive any refactor: command keys are still tokenised and every token judged, because there the path genuinely lives inside the text. Nothing about this relaxes a verdict to `ALLOW`; it changes only where the guard looks. And **the length filter is measured on the FOLDED form** (`GuardPaths.fold`), never on the raw spelling: a `/.`-padded credential path used to be dropped by `MAX_PATH_LEN` before there was anything to fold, and a dropped candidate is not a weaker match but *no rule at all* — credential, command and foreign, all bypassed at once. Measuring before normalising is the classic evasion, so an "optimisation" that restores that order reopens it. Folding is bounded (only past a length threshold, only when the value actually contains `/./`-style noise, and under `MAX_FOLD_LEN`), and that ceiling is not a performance compromise but the point where the string stops being able to name a file at all: Linux refuses any path over `PATH_MAX` with `ENAMETOOLONG` and Windows' extended form stops well short of it, so what falls outside the fold is exactly the set of spellings no syscall will act on.

Only on OPEN, not on re-select. **That init is the ONE command the plugin runs itself**, and it is worth stating next to the sentence above rather than leaving the two to be read together as a contradiction: `GitActionCatalog` marks it `Kind.DIRECT` and `GitIntegration.gitInit` spawns it through `GeneralCommandLine`, so — unlike every other entry — it does NOT pass `can_use_tool` → `SensitiveGuard` → a card. ## JCEF UI (4.0.0)
The chat UI is an embedded Chromium web view (JCEF) — an inlined web app, no CDN, no external resources, under a strict CSP. Kotlin (`ui/jcef/`):
- `JcefHost` — owns the `JBCefBrowser` and the host↔web bridge: an **async `JBCefJSQuery`** for web→host messages, and **frame-batched `cc.batch`** streaming for host→web updates (deltas coalesced and flushed per frame, not per token). Getting the document into the browser is a **ladder, not a mode** (`PageRoute`: `SCHEME` → `LOOPBACK` → `INLINE` → `NOTICE`), because each rung exists for a deployment where the one above it fails — under Remote Development the document lives on the backend and the thin client reaches it through a port forward. `LoopbackPageServer` serves it behind a **one-shot token**, answers any other path with a 404 that has **no body and does not spend the token** (a rejection with a body is a fingerprint of what is being served), and `RemoteDevNotice` is what the client sees when it cannot reach that port — naming the port and the command that fixes it, which the browser's own network error does not, and **carrying no token**. Both invariants are pinned by tests. The script load order and the CSS cascade order are declared here (`appNames`, `CSS_PARTS`) and read out of this file by `scripts/gen-projectmap.py` — never globbed from the directory, because alphabetical is not the same order; a module missing from `appNames` is silently not served, so removing a file means removing its entry in the same change. `whenWebReady(timeoutMs = WEB_READY_TIMEOUT_MS) { … }` is the seam for anything that must wait for the PAGE rather than for the browser (see `ui/` above): each queued block has an identity and is taken out of the queue before it runs, so the page's own announcement and the deadline racing cannot run it twice, and the deadline runs it regardless — a wait for a page that never announces itself must not swallow the gesture.
- `JcefBridge` — **pure** protocol serialize/parse: turns inbound web messages (e.g. `removeAttachment`/`pickFiles`/`attach`/`resolveElicitation`/`mcpReconnect`/`mcpToggle`/`stopTask`/`open`, and 5.5.0's `treeChildren`/`treeExpand`/`attachPaths` for the in-menu project browser) into typed events and back, with no IDE dependencies (so it's unit-testable on the pure JVM — `JcefBridgeTest`). Two rules here are security-shaped rather than parsing details. **Every field read is `as? JsonPrimitive`, never `.jsonPrimitive`**: the latter THROWS on an object or an array, and the input is a browser message, so a field carrying the wrong shape is an ordinary input — thrown from here it escapes `parse` and leaves the gesture with no answer at all. And **`treeChildren`/`treeExpand` validate no path**: containment is `ProjectTree.resolve`'s single gate, and an opinion formed at the wire is the second copy that eventually ends up the weaker one; `attachPaths` (root-relative, a batch) is kept a separate message from `attach` (one ABSOLUTE path, from the recent-files list) rather than sniffed apart at the far end, because a rule that guesses which vocabulary it was handed will one day guess wrong about a path starting with a drive letter.
- JSON builders (kotlinx `buildJsonObject`), all null-safe so a card omits cleanly when data is absent: `JcefState` (composer/transcript state) + `JcefComposerOptions`/`JcefModelLabels`/`JcefCardPayload`/`JcefTranscriptPayload`, `JcefTheme` (the IDE theme as CSS variables), `JcefSessionData` (the dashboard) + `JcefAccountData`/`JcefCostData`/`JcefUsageData`/`JcefWorkloadData`/`JcefPlanData`/`JcefGitData` (one card each; the Git view is drawn from `GitActionCatalog`, the same list the executor dispatches on, and its page module is `app-session-git.js`), `JcefTabsData` (the tab bar), `JcefTreeData` (the two answers the in-menu project browser waits for — each echoing back the `path` and `mode` it answers, because both arrive asynchronously into a menu the user is still driving and an unlabelled reply gets applied to whichever folder happens to be open, a routing bug that looks like a listing bug), `JcefSettingsMenu` (the composer's ⚙ — ten collapsible groups, `radio`/`check` rows, composite `prefix:value` keys verified host-side, and a `deferred` marker on the groups that are launch flags), and `JcefStatus` — **one state vocabulary**, `running|completed|failed|stopped`, decided host-side; the page paints the word it is sent and never derives one. **`JcefTabsData` carries only the SELECTED chat's work**: the second row is the open chat's agents, subagents and background tasks, and nothing on screen asks what another chat started. Each chat used to carry its own `tree` and `tasks` so that hovering a tab you were not in could open that chat's subtree — the panel that did was removed with the `⋮`, leaving a full serialisation of every open session's agent tree on every agent event, several times a turn, for fields the page no longer reads. The whole picture is the dashboard's Workloads diagram, which asks for it when it is on screen.
- `JcefChatPanel` — a **thin assembler** / `SessionListener`: forwards session events to the web app via the host, dispatches inbound bridge messages back to `ClaudeSession`. New behaviour goes in a JS module, a JSON builder or one of the panel's collaborators (see `ui/` above); the panel stays an assembler.

Frontend (`resources/jcef/`, all inlined): `shell.html` (the CSP'd document) + the ES2019 modules listed in `JcefHost.appNames` in **load order, which is a contract** (that declaration is the count — do not restate one here, it goes stale on the next module) (there is no module system in the page — each file is its own hash-pinned `<script>` and they meet through `window.cc`/`window.CC`, so a file that reads another's namespace at load time must come after it; `app-core.js` first, then each family's shared namespace before its members, with the composer's, the dashboard's and the tab bar's SPINE last because they build eagerly on load). The families: **core** (`app-core` bridge helpers + the null-safe `cc.*` registry, `-markdown`, `-diagram`, `-theme`), **transcript** (`app-transcript` + `-rows`/`-tools`/`-links`/`-find`), **composer** (`app-composer-base`/`-menus`/`-pills`/`-attach`/`-readout`/`-palette`/`-boot`/`-auth`/`-actions`/`-settings` + `app-composer`), `app-permissions` (permission/question/**elicitation** cards — URL gated to http/https, form fields from the request schema), **dashboard** (`app-session-base`/`-cards`/`-mcp`/`-workloads`/`-git` + `app-session`), and **tabs** (`app-tabs-base`/`-guard`/`-pill`/`-scroll` + `app-tabs`). `app-tabs-guard.js` is the render skip, kept whole in one file on purpose: it computes a signature of everything drawn — both rows, the chats and the flat row of everything the open chat started — and `render` returns early when it matches, so an identical host push is a no-op instead of a rebuild. **The signature must describe everything drawn and nothing else**, and both directions fail: too little and the skip lies, because a row it does not mention is drawn once and then frozen — an agent that finished keeps its running colour; too much and the skip never fires, which at the dozens of pills that row exists for is a full rebuild several times a second, the reported flicker. So the rule for editing either file is one sentence: what the row starts drawing starts appearing in the signature, and what it stops drawing stops appearing there. Pinned by the DOM-identity tests in `tabs.test.js`. The dashboard has the same discipline in `renderIfShown()`: while hidden the payload is stashed, not drawn. **Two rules govern anything the host re-pushes, and both were learned by breaking them.** (1) *A container that gets rebuilt loses where the reader was*: a fresh element is born at offset 0, so the offset is read before the teardown and put back after — the dashboard panel and the tab capsule both do this, and the capsule's restore must be instant because `.tab-capsule` declares `scroll-behavior: smooth` and a plain assignment would turn every repaint into a visible glide. The tab row also re-centred the selected chat on EVERY render rather than on a change of selection, so dragging to a far tab and receiving any agent event snapped the row back and re-aimed it. (2) *`appendChild` on a node already in place is not a move*: the DOM has no move, so it is a remove plus an insert — measured in jsdom as `[removed 1, added 1]`, with the focused input inside the subtree blurred, which is exactly what Chromium does and precisely why `moveBefore()` exists. Reconciling permission cards that way reset the capped `.perm-diff` body to its first line and dropped the caret every time a second request arrived, i.e. while the user was reading that diff or filling in that elicitation field. Only a card whose position actually changed is moved now. Plus `css/*.css` — concatenated in **cascade order** (that list is the count; `git.css` sits sixth and its position is load-bearing, documented at the declaration) by `JcefHost.CSS_PARTS`, one `<style>` block, hash-pinned like the scripts — and **vendored** `marked`/`highlight.js`/`DOMPurify` (model text is rendered via `marked` then sanitized with `DOMPurify`; links never navigate — they route through `CC.send({type:'open',url})`). Diffs stay native via `DiffManager` (unchanged).

Consequences worth knowing: a failed READ is not an empty configuration (`readFailed` refuses the next save, or one bad read at startup became a permanent overwrite), the legacy file is deleted only after the safe accepts the copy (`secret_password_store_sync error code 36` lost a configuration on this box, and `set` reports failure to nobody), and every mutation goes through `update {}` — a bare `state.x = y` is a change that silently does not survive a restart, which is exactly what the three "Always allow" mutators were doing. Then the fixes this release's own work needed: **a nested subagent never stopped RUNNING** (it has no `toolUseId`, so nothing could ever settle it — its parent's ending settles it, since it cannot outlive the turn that spawned it. **Only the ENDING, and only for a child that never closed a turn of its own**: copying the parent's state outright, before the child's own transcript was read, meant a subagent that had finished reported RUNNING for as long as its parent worked — which is what a subagent DOES — and everything reading that node repeated it, the tab dot, the Task card and a Workloads row the window cannot expire. An ending of its own outranks the parent's, and a RUNNING parent settles nothing: it is only evidence that there is a live process behind the child. The binary does not always give one this can key on: `tool_use_id` is optional on that message and several of its call sites pass none, and the `Agent` tool's own `tool_result` is no substitute — measured against a real session, it returns **10 ms** after the call while the agent runs for half an hour, which is why `onToolResult` deliberately does not settle a card that belongs to an agent. ## Protocol gotchas (load-bearing, verified)
- `--print` is required alongside stream-json in/out; `--permission-prompt-tool stdio` confirmed.
- `system/init` arrives **every turn** and reports the launch-time `permissionMode` — never block on it (historic deadlock: `start()` sets `ready=true` at startup) and never adopt its mode (the plugin is the source of truth, else the "reset to default" bug).
- **`AskUserQuestion` comes through `can_use_tool`** (not `request_user_dialog`): respond `allow` with `updatedInput={...input,"answers":{question:label}}` (comma-separated if multiSelect); without `answers` the model improvises.
- **`request_user_dialog`** (open-union `dialog_kind`) is answered `{behavior:"cancelled"}` — the host renders no custom kinds, so the CLI applies the dialog's own default. **`elicitation`** (MCP user input) is answered with an `ElicitResult` `{action:accept|decline|cancel, content?}`, surfaced as a non-modal tray card (URL link gated to http/https; form fields from `requested_schema` primitives). Both were previously rejected with an error. Pending elicitations are default-cancelled on session teardown so the binary never hangs. The full triaged subtype surface lives in `ProtocolSurface.KNOWN_SUBTYPES`; `./gradlew checkDrift` flags anything new.
- **`/btw` is the `side_question` control request, and it has to be** — not a `user` line. `TranscriptReconciler.belongsHere(parentToolUseId) = parentToolUseId == null` discards every block the binary does not label as the main run, which is the filter that keeps a subagent's output out of this transcript; a side answer is answered by a worker of its own, so it is on the wrong side of that filter **by construction** and written as a user line it was simply never rendered. Relaxing the filter would re-open the interleaving it exists to prevent, so the channel changed instead: `side_question` **returns** the text in its control response, and it is painted as a SYSTEM notice with `↩` rather than as a turn — `turnActive` is untouched, so the composer does not claim the session is working and a real turn running alongside keeps its own state. A refusal, a blank answer or the 30 s watchdog produces a stated non-answer, because a question with no reply under it reads as one the plugin forgot. It is also what `system/control_request_progress` reports the progress OF; until this existed the plugin modelled the progress of a request it never sent.
- **`generate_session_title` and `side_question` are declared in `sdk.mjs` and NOT in `sdk.d.ts`.** The published types cover the thin client's requests, so `SdkDrift` cannot see these two and lists them as *stale* — informational, and deliberately not enough to make a run actionable. They are in `ProtocolSurface.KNOWN_SUBTYPES` regardless: that set is the inventory of what the plugin puts on the wire, and a subtype missing from it is a subtype nobody triaged.
